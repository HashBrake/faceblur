# TensorRT FP16 trial on the RTX 5090, 2026-10-16 (T12)

A time-boxed trial on the cloud VM `faceblur-dev-b-1` (RTX 5090, driver
580.159.04, 32607 MiB), run right after the T12 benchmark
(`docs/bench/speed_2026-10-16_5090.json`). The question: does running the
detectors through onnxruntime's TensorRT execution provider in FP16, instead of
the CUDA execution provider, make detection worth changing for? No file under
`faceblur/` was changed. T13 decides on the basis of these numbers.

Short answer: TensorRT FP16 works, gives the same confident detections, and
saves 5 to 8 % of `DetectorBank.detect_raw` time per frame. Most of the
per-frame cost is outside the model run.

## Setup

- Image `vcr.vngcloud.vn/110156-faceblur/faceblur-cuda:3`: Python 3.12, onnxruntime-gpu
  1.24.4 (built for CUDA 12.8). `ort.get_available_providers()` lists
  `TensorrtExecutionProvider`, `CUDAExecutionProvider` and `CPUExecutionProvider`.
- The image has no TensorRT runtime: there is no `libnvinfer` anywhere in it, and
  the TensorRT provider library (`libonnxruntime_providers_tensorrt.so`) needs
  `libnvinfer.so.10`.
- The PyPI `tensorrt-cu12-libs` package is an sdist that downloads the real wheel
  from NVIDIA. That wheel,
  `tensorrt_cu12_libs-10.16.1.11-py3-none-manylinux_2_28_x86_64.whl` (4.30 GB),
  was downloaded from `pypi.nvidia.com` to the VM's disk with curl at about
  30 MB/s. It was then installed inside a throwaway `--rm` container only, with
  `pip install --no-deps --no-index --target /w/trt_pkgs <wheel>` (59 s). Nothing
  was installed on the host or into the image. `/w/trt_pkgs/tensorrt_libs` holds
  `libnvinfer.so.10`, `libnvinfer_plugin.so.10`, `libnvonnxparser.so.10` and the
  builder resources (sm75 to sm120).
- Every trial container ran with
  `-e LD_LIBRARY_PATH=/w/trt_pkgs/tensorrt_libs:/usr/local/cuda/lib64`, with the
  branch checkout (commit 40986ae) mounted at `/w` and `PYTHONPATH=/w`.

## Method

- Input: `ego_AZER76400FE_19700101_004100_camera_left_part0001.mp4`, the first
  60 frames, decoded with `faceblur.segments.decode_range`. These are the real
  frames, 1600x1300. After `resize_long_side` and the pad to 32, the model inputs
  are 1568x1920 (det size 1920) and 1056x1280 (det size 1280), not 1920x1088.
- Two provider lists are compared:
  - CUDA: `["CUDAExecutionProvider", "CPUExecutionProvider"]`
  - TRT FP16: `[("TensorrtExecutionProvider", {"trt_fp16_enable": True, "trt_engine_cache_enable": True, "trt_engine_cache_path": ...}), "CUDAExecutionProvider", "CPUExecutionProvider"]`
- The providers were set at run time and not in the code. The trial script
  builds the normal `YuNetOrtBackend` or `DetectorBank(Settings(device="gpu"))`,
  replaces `pool.providers` on each `SessionPool` instance, and clears
  `pool._sessions`. The pool's own `_make` then builds the static-shape sessions
  as in production.
- `_make` is wrapped so that each static shape gets its own engine cache folder,
  `/w/trt_cache/<model>_<n>x<h>x<w>`, created before the session is made
  (finding 1 below explains why). The folders written were
  `yunet_dynamic_1x1568x1920`, `yunet_dynamic_1x1056x1280`,
  `centerface_dynamic_8x224x224` and `ultraface_dynamic_8x240x320`. Their
  presence confirms that each model really ran on TensorRT.
- Timing: 5 warm-up calls, then the mean over the 60 frames. `detect_resized`
  includes the blob copy, the model run and the decode plus NMS. The raw `run`
  is `pool.run` on one fixed blob. `detect_raw` is the full bank call at both
  det sizes, with the CenterFace and UltraFace crop confirmation.
- The trial script and the raw results are kept outside git, in
  `bench_out/5090/trt/` (`trt_trial.py`, `warm.py`, `trt_result.json`, logs).

## Results

### YuNet, per frame

| | CUDA EP | TRT FP16 |
|---|---|---|
| `detect_resized` at 1920 | 12.78 ms | 11.12 ms |
| raw session `run` at 1920 | 4.23 ms | 3.58 ms |
| `detect_resized` at 1280 | 5.06 ms | 5.99 ms |
| raw session `run` at 1280 | 2.24 ms | 1.78 ms |

### `DetectorBank.detect_raw`, per frame

| | ms per frame |
|---|---|
| CUDA | 38.67 |
| TRT FP16 on YuNet only | 36.57 (-5 %) |
| TRT FP16 on all three models | 35.45 (-8 %) |

### Detections, CUDA vs TRT FP16 (YuNet, boxes at the 0.05 floor)

| det size | boxes CUDA / TRT | frames whose count differs | boxes >= 0.4 CUDA / TRT | max score change on IoU >= 0.5 matches | CUDA boxes >= 0.3 with no TRT match |
|---|---|---|---|---|---|
| 1920 | 1372 / 1360 | 12 of 60 | 85 / 85 | 0.0501 | 0 |
| 1280 | 736 / 738 | 8 of 60 | 44 / 44 | 0.0203 | 0 |

In `detect_raw`, YuNet finds 1483 boxes over the 60 frames on CUDA and 1476 on
TRT. The confirming detectors' counts over the 60 frames:

| | CUDA | TRT on all three |
|---|---|---|
| centerface | 117 | 119 |
| centerface_flip | 86 | 86 |
| centerface_tight | 76 | 78 |
| ultraface | 43 | 47 |

The differences are all in low-score boxes. Every box at 0.4 and over is the
same in both, and no CUDA box at 0.3 or over goes missing.

### Engine build times

| | first call |
|---|---|
| YuNet 1568x1920, engine built | 9.237 s |
| YuNet 1056x1280, engine built | 9.128 s |
| YuNet either shape, engine from the cache | 0.07 s |
| first `detect_raw`, all three models' engines built | 21.64 s |
| smoke test, YuNet 64x64, engine built | 12.07 s |

For comparison, the first CUDA call at 1568x1920 in a fresh process took
51.3 s (see finding 3).

## Findings for whoever implements this

1. **The engine cache key has no shape in it.** For a model passed as bytes
   (which is what `SessionPool._make` does, after it rewrites the dimensions), the
   TensorRT provider's engine cache key leaves out the input shape. On the first
   attempt, a cached 1x3x1088x1920 engine was reused for a 1x3x1568x1920 input
   and failed in `IExecutionContext::setInputShape` with "Static dimension
   mismatch". Give each shape its own `trt_engine_cache_path` (the trial's fix)
   or its own `trt_engine_cache_prefix`. The provider also does not create a
   missing cache folder recursively: create it first.
2. **The fallback to CUDA is silent, and the reported provider is wrong.** When
   the TensorRT provider fails to create a session (a missing cache folder did
   this), onnxruntime prints an "EP Error" banner, falls back to
   `["CUDAExecutionProvider", "CPUExecutionProvider"]` and carries on. Separately,
   `DetectorBank.compute` reported `CUDAExecutionProvider` for every model even
   when TRT was running, because each backend's `provider` attribute is copied
   from the pool at init and never updated. Check the session's
   `get_providers()` (or the pool's `provider` after the first `run`) and fail
   loudly if TensorRT was asked for and is not first.
3. **The first CUDA call costs 46 to 52 s at 1568x1920.** In a fresh process
   (and a fresh `--rm` container), the first YuNet call on the CUDA provider at
   1568x1920 took 51.3, 51.8 and 52.2 s across runs. A second session in the
   same process then takes 0.2 s, and 1280 right after 1920 took 0.06 s. What
   was tried:
   - `cudnn_conv_algo_search=HEURISTIC`: 51.7 s, no change.
   - A persistent `CUDA_CACHE_PATH` (2 GB) mounted from the host, run twice:
     8.4 s, then 46.4 s. It wrote 95 MB.
   The cause is not settled. CUDA JIT compilation for sm_120 is the obvious
   suspect, but the cache test did not confirm it. TensorRT's 9 s per engine
   (0.07 s once cached) is well below this. In production this may be a fixed
   cost per container, or per worker process.
